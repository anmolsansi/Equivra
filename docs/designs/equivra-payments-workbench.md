## Problem Statement

Build a local web workbench that helps a reviewer investigate differences between payment processor, bank, and accounting exports. A selected refund, dispute movement, or settlement difference must be explainable through source records; insufficient evidence must remain visible.

The initial audience is the founder demonstrating backend engineering to interviewers. A bookkeeper is the modeled operator. Small bookkeeping firms are a business hypothesis, not verified customers. This document is a product design proposal, not implementation authorization or a delegation-ready specification.

## What Makes This Cool

The demo tells a financial story and proves it: follow a partial refund into a payout, inspect a missing or ambiguous bank reference, and retain an honest unresolved result. Then replay the import or interrupt processing and show that the evidence and amounts remain correct. The same reproducible fixtures can become an interview walkthrough, a regression suite, and a failure-recovery demonstration.

## Proposed First Product Slice

The founder approved this product design at D8. Implementation details still require refinement in the requested reviews. No endpoint, schema, framework version, or financial rule is frozen here.

### Demonstration boundary

- One synthetic client workspace, one Stripe source account, USD only, and one explicitly declared investigation period plus necessary adjacent-period evidence.
- Three documented CSV input formats: a selected Stripe automatic-payout itemized export shape, a synthetic bank format, and a synthetic accounting format. Do not claim universal bank/accounting import support.
- The accounting export is a required evidence source, not an unused upload: compare supplied processor refund references with the provided book entries, surface missing or inconsistent book evidence, and show those source rows in the case view. Absence from an export is not proof the entry never existed.
- Preserve original file and row references, source values, mapping version, and run version. A correction creates a new version rather than rewriting approved evidence.
- One local reviewer workflow. Public sign-up, SaaS tenancy, and multiuser deployment are later proposals. Concurrent review behavior can be exercised using controlled test clients against the same local case.
- Treat missing evidence, ambiguous relationships, and unsupported records as explicit unresolved outcomes. A balanced total alone cannot establish completeness or a supported match.

### Core journey

```text
Select synthetic example / upload documented CSV bundle
                       |
                Validate + preview
                 /             \
       Invalid or missing      Accepted inputs
       Show source + issue           |
       Correct and retry       Queue processing
                                     |
                         Exception queue + run status
                                     |
                         Evidence rows and timeline
                                     |
                       Reviewer records a disposition
                                     |
                  Reviewer freezes reviewed workpaper
                                     |
                    Immutable HTML/CSV report snapshot
```

Accepting a review disposition records what the reviewer concluded; it does not manufacture a financial match, post a journal, certify the books, or turn missing evidence into supported evidence.

Proposed approval boundary: saving a case disposition does not approve a report. A separate **Freeze reviewed workpaper** action fixes the selected run, input/mapping/rule versions, evidence references, and saved dispositions into an immutable report snapshot. The interface labels remaining unresolved cases in that snapshot; it never equates freezing with a fully reconciled result. Export renders that fixed snapshot. Corrections or new dispositions produce a new reviewable version and require a new freeze action; a stale freeze request fails visibly instead of capturing an unintended newer state. This product behavior is proposed for founder approval, not a frozen API contract.

### Evidence and financial correctness

- Use exact monetary representation and explicit currency. Reject unsupported currencies and invalid precision rather than rounding silently.
- Preserve event time, payout timing, bank posting time, and accounting date distinctly. Period cutoff differences are not automatically losses.
- Prefer explicit identifiers and documented payout membership. Same amount alone is insufficient to resolve a relationship.
- Prevent repeated source events or processing retries from consuming the same amount twice. Identical legitimate transactions must remain distinct when their source identities differ.
- Preserve an approved report's source snapshot, rules/version references, and reviewer decisions so later imports do not change it.

### Proposed scenario set

| Scenario | Observable outcome |
|---|---|
| Partial refund | Supplied signed amounts and relationships are traceable; no invented fee refund |
| Processor refund missing from supplied accounting entries | Case shows the processor refund row and the searched accounting evidence scope; missing book evidence remains unresolved until supported, without claiming the real books lack the entry |
| Dispute withdrawal and later reversal | Separate movements remain visible; no double-counted permanent loss |
| Payout and bank deposit cross a period boundary | Timing remains explicit; adequate adjacent evidence can support a relation |
| Two deposits share an amount | Remains ambiguous without sufficient references |
| Missing source detail or malformed input | Explicit validation/coverage issue; no guessed supported result |
| Repeat import, correction, or interrupted processing | No duplicate economic result; prior approved evidence is preserved |
| Competing reviewer submissions | Stale update is rejected rather than silently replacing a decision |

## Architecture Shape

One backend codebase, with an API process and a worker process. The worker executes durable jobs backed by PostgreSQL. Use an established queue library if its transaction and retry behavior fits; do not invent a queue before evaluating existing options. Exact library, transaction boundary, retry policy, and recovery semantics belong in the architecture review.

```text
Browser: React review UI
            |
     TypeScript API ------> local source storage
            |                     |
       PostgreSQL <------- TypeScript worker
       facts / jobs         parse / validate / investigate
       runs / reviews       render approved reports
```

The API and worker share explicit domain contracts and database migrations. They are processes within one application, not independently owned microservices. No Redis, Kafka, Kubernetes, vector database, or agent framework is proposed for this slice.

Local source storage must not become an arbitrary path reader. The implementation plan must specify generated storage identifiers, upload limits, safe parser behavior, output escaping, and a loopback-only access boundary. These remain mandatory design work before implementation, not proof of safety today.

### User-visible states

| Area | States the implementation design must cover |
|---|---|
| Import | Empty, validating, rejected with row issues, accepted, duplicate, revised |
| Processing | Queued, running, retrying, failed with reason, completed |
| Investigation | No differences, supported relationships, unresolved, incomplete evidence |
| Review | Unreviewed, saved disposition, stale submission conflict |
| Report | Draft, freeze conflict, frozen snapshot, generating export, export available, export failed |

State names are conceptual. Exact transitions and contracts must be locked before task generation.

## Success Criteria

The proposed slice is successful when an unfamiliar viewer can follow an import through evidence review to an exported report and the following assertions are proven:

1. Every reported financial fact traces to source rows or an explicitly documented deterministic calculation.
2. Invalid or incomplete data cannot be labeled fully supported; ambiguous same-amount records remain unresolved.
3. Repeating an import or recovering an interrupted job adds no duplicate financial result.
4. Corrected input creates a new version and does not mutate the prior approved report.
5. A competing stale reviewer submission cannot silently overwrite a saved disposition.
6. Recreating a report from its recorded snapshot reproduces its financial facts and evidence references.
7. A clean local setup can run the documented synthetic demo with its documented commands.
8. The walkthrough uses all three sources: a processor-to-bank relation plus an accounting-side refund discrepancy, including an explicit distinction between missing export evidence and a proven missing book entry.
9. Saving a disposition leaves the report in draft. Freezing creates the immutable reviewed snapshot; subsequent edits require a new version, and a stale freeze cannot silently capture changed evidence.

These are approved product acceptance criteria, not measured achievements. Exact tests, schemas, and commands remain to be established. AI quality and commercial demand are not implied by passing them.

## Milestones and Effort

Order the work by demonstrable outcomes, with behavior tests in every milestone:

1. Define input contracts and expected synthetic scenarios; establish the minimal runnable application and verification commands.
2. Persist and validate a source bundle; expose a useful preview with actionable failures.
3. Produce deterministic investigation results with evidence links and visible uncertainty.
4. Complete the review and report journey; verify correction/version and stale-review behavior.
5. Demonstrate replay and worker interruption/recovery; finish the reproducible walkthrough and documentation.

The previously offered allowance was 60–100 hands-on hours with AI assistance, roughly 6–10 weeks at 10 hours/week; without AI assistance, 90–140 hours. These are unvalidated planning estimates, not a schedule commitment. Domain-rule review and integration failures may raise them. Re-estimate after contracts and the first runnable slice. No performance claim or benchmark target is accepted yet.

## Distribution Plan

Initial delivery is a reproducible local repository checkout with synthetic fixtures, an example configuration, setup/reset instructions, and a short demo recording. Proposed CI runs the behavior tests and build checks once actual tooling is selected. Publishing a repository, release, recording, container image, or hosted site requires the corresponding later user instruction; no publication happens in this design step.
